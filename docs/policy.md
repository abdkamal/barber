# ملخص سياسة بناء المشاريع

المصدر: «سياسة بناء المشاريع.docx»، مع توضيحات المستخدم بشأن اعتماد نسخة التطوير وتنظيم المتابعة البشرية. اقتراحات الأدوات والتعديلات الأخرى ليست معتمدة تلقائيًا.

## 1. الهدف

تطبيق مبادئ هندسة البرمجيات، وتقسيم المشروع إلى طبقات ومراحل، والوصول إلى نموذج أولي (Prototype) واضح قبل التنفيذ؛ لتقليل التعديلات وإعادة العمل، والاستفادة من التوكن قدر الإمكان دون خفض الجودة.

## 2. المبادئ الأساسية

1. **المشرف:** نموذج قوي بدور Orchestrator يدير المشروع.
2. **الاقتصاد:** تكليف النماذج الاقتصادية بالمهام البسيطة دون التأثير على الجودة.
3. **التحقق:** المشرف يستلم النتائج ويفحص جودتها ومطابقتها للمواصفات.
4. **تعدد المزودين:** إمكان تكليف نماذج من شركات أخرى عبر CLI.
5. **استقلال المراجعة:** نموذج قوي آخر يراجع الخطة المتفق عليها مع المستخدم، ثم تعود الملاحظات للمشرف للمراجعة والمناقشة والاعتماد الأخير.
6. **الإذن الصريح:** لا برمجة قبل اعتماد التصميم وموافقة المستخدم النصية الصريحة على البدء.
7. **وضوح المتطلبات:** مناقشة الفكرة وتفاصيلها بدقة مسبقًا لتقليل التغييرات أثناء التنفيذ.
8. **استمرار التنفيذ:** متابعة العمل إلى نقطة التسليم المتفق عليها، مع احترام بوابات الموافقة ودون توقفات روتينية لطلب الإذن.
9. **الأمن والجودة:** بوابات صارمة وواضحة لتسجيل الدخول والتشفير ومنع الاحتيال ومحاولات الاختراق وتجاوز أمان النظام، وفحوص جودة صارمة.
10. **التوازي:** تشغيل عدة وكلاء بالتوازي عندما يحقق ذلك كسبًا في الوقت.
11. **تجربة الاستخدام:** تعليمات وتنويهات واضحة داخل البرنامج، خصوصًا في أول إصدار؛ وسهولة استخدام ومرونة وموثوقية، ودعم كامل للعربية والنصوص العربية والإنجليزية المختلطة وRTL.
12. **دليل المستخدم:** تسليم دليل واضح للاستخدام والمحددات والتحذيرات.
13. **متابعة التقدم:** عرض المرحلة الحالية والمنجز والمتبقي.
14. **حفظ التقدم:** حفظ دوري للتقدم في Git.

## 3. مراحل العمل

| المرحلة | المطلوب |
| --- | --- |
| 1. التخطيط | مناقشة الفكرة والأسئلة والتفاصيل، وتحديد المواصفات والمنصات وقواعد البيانات والواجهات وبيئة التطوير وسرية البيانات ومتطلبات التشفير. |
| 2. اعتماد الخطة | مراجعة مستقلة بواسطة نموذج قوي، ثم دراسة الملاحظات ومناقشتها مع المشرف وصولًا إلى الاعتماد الأخير. |
| 3. تجهيز البيئة | فحص توافر المتطلبات والأدوات اللازمة على الحاسوب. |
| 4. تصميم الواجهات | تصميم تجربة الاستخدام والواجهات لجميع المنصات المعتمدة، وعرض التصميم لاعتماد المستخدم. |
| 5. تنفيذ الكود | البدء بعد اعتماد التصميم والموافقة النصية الصريحة. |
| 6. مراجعة الكود | مراجعة بواسطة نموذج مستقل. |
| 7. ربط الواجهات | ربط الواجهات بالكود البرمجي. |
| 8. كتابة الاختبارات | إعداد اختبارات لسيناريوهات محددة. |
| 9. تشغيل الفحوص | الاختبارات والتجميع اللازم للتطوير والفحوص، والاختبارات الأمنية وفحص الاختراق. |
| 10. مراجعة النتائج | مراجعة مستقلة لنتائج الاختبارات وإعادتها للمشرف للدراسة والإصلاح. |
| 11. تجربة نسخة التطوير | تجربة المستخدم للنسخة، وتقديم ملاحظاته وتصحيحها وإعادة عرضها إلى حين اعتماده لها. |
| 12. بناء الإصدار والتسليم | بناء إصدار التسليم وحزمه بعد اعتماد نسخة التطوير، وتسليمه مع دليل الاستخدام. |
| 13. تنظيف المشروع | تنظيف الكود والملفات الزائدة. |

ترتيب المراحل محفوظ من المصدر؛ نقل التنظيف إلى مرحلة أخرى اقتراح يحتاج اعتمادًا منفصلًا.

## 4. بوابتا الموافقة

**قبل البرمجة:** اعتماد الخطة والتصميم والنموذج الأولي، ثم موافقة المستخدم النصية الصريحة على بدء التنفيذ.

**قبل بناء إصدار التسليم وحزمه:** يجب أن يجرّب المستخدم نفسه نسخة التطوير، وتُعالج ملاحظاته، ثم يعتمدها صراحة. لا يعتمد المشرف النسخة نيابة عنه، ولا تُعد موافقة التصميم اعتمادًا للمنتج المنفَّذ.

يسمح بالتجميع اللازم لتشغيل نسخة التطوير وتجربتها؛ أما بناء إصدار التسليم النهائي (Release) وحزمه، بما في ذلك Setup، فبعد الاعتماد فقط.

**التسلسل:** اعتماد التصميم ← إذن البرمجة ← تنفيذ نسخة التطوير وفحصها ← تجربة المستخدم وتصحيح الملاحظات ← اعتماد النسخة ← بناء إصدار التسليم وحزمه وتسليمه.

## 5. تنظيم المتابعة البشرية

| الفترة | دور المستخدم والمشرف |
| --- | --- |
| البداية | المستخدم يحدد الاحتياجات ويجيب عن الأسئلة ويراجع الخطة والتصميم ويوافق على بدء التنفيذ. |
| أثناء التنفيذ | المشرف والوكلاء ينفذون وفق المتطلبات والقواعد، مع إتاحة متابعة التقدم دون مقاطعات روتينية. تُرفع القرارات المؤثرة التي تحتاج موافقة المستخدم. |
| اكتمال نسخة التطوير | المستخدم يجرّب البرنامج ويقدم ملاحظاته ثم يعتمد النسخة بعد تصحيحها. |
| بعد الاعتماد | المشرف يستكمل بناء إصدار التسليم وحزمه وتسليمه وفق العقد المتفق عليه. |

استقلالية المشرف لا تسمح بتغيير المتطلبات أو تجاوز بوابات الموافقة.

## 6. تطبيق السياسة في المشاريع

المطلوب تحويل السياسة إلى Skill أو آلية مشتركة دون إعادة شرحها. يبقى تحديد التوزيع التفصيلي للمهام على النماذج، واختيار الأدوات، وتقييم `amElnagdy/delegate-skills` قيد الحسم؛ هذا الملخص لا يعني تنفيذ المهارة أو اعتماد أداة بعينها.
